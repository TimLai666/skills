# Plan: 強模型定骨架、弱模型填細節的開發模式

## Problem

目前 agent-delegation 規定主 agent 不寫程式，把工作切成每張約 200 行、只驗一個行為的 ticket，交給免費模型逐張完成。新專案、新功能與修正都走這條路，結果常見兩種狀況：

- 整體結構在還沒有任何能跑的東西之前就定死，ticket 之間的銜接要到後期才發現對不上。
- 修正交給弱模型時，只處理被指出的那一處，根因、同類位置與邊界情況沒有一起處理。

## Reframe

問題不在「切」，在「太早切、切太細」，以及範圍與完整性交給了最不擅長判斷的弱模型。改成由負責派工的主 agent 決定範圍與驗收，弱模型只負責照規格填實作。

這不只是派工規則，而是所有開發的原則：每次以一個完整的功能或問題為單位，先定骨架與驗收，再一次做完整。有沒有派工，都照這個原則做。

## Scope decisions

### Chosen scope

- 開發原則寫進 software-engineering-guidelines：以一個完整的功能或問題為單位，先骨架與驗收再填實作，修正一次處理根因、同類位置與邊界情況，範圍外的只回報 - 沒有派工時也適用。
- 全域指令 `agents-prompts/AGENTS-content.md:107`「以小範圍、可驗證的改動推進」改成與此原則一致 - 原句直接衝突。
- 派工細節寫進 agent-delegation：測試 agent 與實作 agent 分開、審查檢查點、派不派的判斷 - 只在有派工時適用。
- 主 agent 在新專案、新功能與修正時，都先寫出從頭到尾能跑的骨架 - 範圍由強模型一次鎖定，不留給弱模型判斷。
- 骨架的每個格子附函式簽名與「想要的結果」清單，虛擬碼想到才附 - 讓弱模型不必做設計決定，也不逼強模型提前想實作。
- 骨架另附兩三條完整使用流程的驗收 - 每格都過不代表整體能動。
- 骨架盡量讓格子落在不同檔案 - 讓多個實作 agent 能同時開工。
- 測試 agent 依「想要的結果」寫測試，實作 agent 另一個 - 實作者碰不到測試，無法改測試過關。
- 主 agent 在實作前審測試，並在空格子上跑一次確認全部失敗 - 擋下翻錯或怎樣都會過的測試。
- 實作 agent 認為測試錯時停下回報，由主 agent 裁決 - 實作者不得改測試。
- 主 agent 判斷派出去不划算時（邏輯很短、交代成本高於直接寫），自己寫 - 避免流程比工作本身還重。
- 修正套同一模式：主 agent 查根因，列出所有要改的位置與驗證，再交給弱模型照改；說不清楚的修正由主 agent 自己改。
- 沒有測試環境或畫面類工作，用可執行的驗證步驟取代測試。

### Explicitly out

- 不指定哪個模型是強模型 - 派工的主 agent 就是強模型，任何 CLI 都可能擔任。
- 不規定主 agent 的做事細節 - 只保留護欄：先定驗收、審查弱模型產出、不派給自己所在的 CLI、實作者不改測試。
- eng-architect 不改 - 它已經按功能切成貫穿各層的 ticket，與本模式相容。

### Deferred

- 記錄弱模型失敗類型來調整派工 - 試跑累積資料後再評估。

## Assumptions to validate

- 測試 agent 加實作 agent 加主 agent 審查，總成本低於主 agent 直接寫 - 若不成立，派工門檻要提高。用一個真實功能試跑比較。
- 弱模型照「想要的結果」寫出的測試品質可用 - 若常被退回，改由主 agent 寫關鍵測試。
- 骨架階段能鎖住大部分範圍 - 若填格子時常發現骨架設計錯，骨架要附更多介面細節。

## Success criteria

在一個真實專案的一個功能上照新流程跑完：

- 完整使用流程的驗收全部通過。
- 實作 agent 沒有改到測試檔。
- 回報列出各階段實際派工、退回次數與主 agent 自己寫的格子，供判斷是否調整門檻。

## Failure modes

- 測試 agent 寫出空格子也會過的測試 - 實作前在空格子跑一次，有通過的退回重寫。
- 各格各自通過但串起來錯 - 完整使用流程驗收在最後必跑。
- 主 agent 每格都派，來回成本過高 - 規則給出「自己寫」的判斷標準。
- 骨架設計錯在填格子時才浮現 - 實作 agent 停下回報，主 agent 改骨架後重派。

## Decisions

### 寫程式的主力
- Decision: 派工的主 agent 先寫骨架並鎖範圍，弱模型填細節。
- Reason: 範圍與完整性需要判斷，弱模型最不擅長；填實作才是便宜模型省得到錢的地方。
- Important alternative: 主 agent 一次寫完整個功能、弱模型只做後續修正。弱模型做「全面修正」會回到只改一點點，因此不採用。

### 測試由誰寫
- Decision: 主 agent 給簽名與想要的結果，獨立的測試 agent 寫測試，實作 agent 另派。
- Reason: 減輕主 agent 負擔，並讓實作者無法改測試過關。
- Important alternative: 主 agent 自己寫所有測試。前期負擔太重，因此不採用。
